# Speaker identification (diarization) — optional.
# If these are absent the app falls back to pause-based speaker detection.
#
# pyannote.audio replaced the old pitch/MFCC + fixed-k KMeans backend in
# masterplan 2.12, after that backend was measured collapsing four confirmed
# distinct voices into a single speaker. It must be 4.x, NOT 3.x: 3.x needs
# huggingface_hub<1.0 (we pin 1.24.0 deliberately, see the note below) and
# torchaudio.AudioMetaData, which no longer exists in the torchaudio that ships
# with torch 2.13.0+cpu. 4.0.7 was verified running on this file's exact pinned
# set — numpy 2.4.6, scipy 1.17.0, huggingface_hub 1.24.0, torch 2.13.0+cpu —
# not merely assumed compatible.
#
# NOTE: pyannote 4.x lists torchcodec as a dependency for its own audio
# decoding, but that wheel is linked against CUDA and will not load on a
# CPU-only install. diarization_engine.py therefore decodes with the bundled
# ffmpeg and hands pyannote an in-memory waveform instead. That is deliberate
# and documented there — do not "fix" it by passing file paths.
#
# ⚠ torchaudio MUST be installed from the CPU-only index, exactly like torch and
# for exactly the same reason — it is NOT listed here, for the same reason torch
# is not. pyannote.audio depends on torchaudio, so a plain
# `pip install pyannote.audio` pulls the DEFAULT (CUDA) build from PyPI, whose
# native `_torchaudio.abi3.so` then fails to load against our CPU-only torch
# with "libcudart.so.13: cannot open shared object file". That is not a
# theoretical hazard: it happened during 2.12's integration and broke three
# previously-green test suites (guard, memory, engine) until torchaudio was
# reinstalled from the CPU index. Install it alongside torch:
#     pip install torch==2.13.0 torchaudio --index-url https://download.pytorch.org/whl/cpu
# Verify with: python -c "import torchaudio" — it raises loudly if wrong.

# scipy pinned explicitly — it was the invisible constraint behind the whole
# numpy drift. librosa and scikit-learn both depend on it, but nothing pinned it,
# so pip was free to pick a scipy whose own numpy floor silently dictated ours.
#
# 1.17.0 is the HIGHEST scipy that satisfies every constraint at once:
#   * numpy<2.7,>=1.26.4  -> accepts our numpy 2.4.6
#   * requires_python >=3.11, and ships a cp311 Windows wheel
#
# That last point is the binding one and is easy to miss: the CI build runs on
# Python 3.11 (.github/workflows/build-windows-release.yml), and scipy 1.18 —
# which is what a fresh `pip install` resolves to, and what was sitting in the
# dev venv — requires Python >=3.12 and publishes NO cp311 wheel. Pinning the
# installed 1.18.0 would have broken the Windows build while passing every test
# on this 3.12 machine.
#
# Upper bound to respect when bumping: numba 0.66.0 caps numpy at <2.5, so do not
# adopt a scipy that requires numpy>=2.5. Bump scipy and numpy together, and
# check the cp311 wheel exists unless CI has moved to a newer Python by then.
scipy==1.17.0

# numpy 2.x ON PURPOSE — this moved from 1.26.4, do not revert it casually.
#
# The 1.26.4 pin was never actually exercised: the venv every Accurate-mode wave
# was built and tested in was assembled ad-hoc for the spike, not from this file,
# and pip resolved numpy/numba/llvmlite/soundfile to latest. So the four pins
# below and the tested reality had silently diverged across a numpy MAJOR version.
# Reconciled deliberately in favour of the tested set, after checking:
#
#   * numba 0.66.0 declares numpy<2.5,>=1.22 and llvmlite<0.49,>=0.48.0dev0, so
#     2.4.6 + llvmlite 0.48.0 is inside its supported window. (The old pair,
#     numba 0.64.0 + llvmlite 0.46.0, was internally consistent too — it was not
#     broken, just untested.)
#   * scipy is the constraint that actually forces the issue: scipy 1.18 requires
#     numpy>=2.0.0. Holding numpy at 1.26.4 silently pins scipy back to <=1.17
#     forever. scipy is NOT pinned in this file, which is how that stayed hidden.
#   * soundfile only declares `numpy` unpinned — it is a thin CFFI wrapper and is
#     not numpy-major sensitive.
#   * openai-whisper, librosa, scikit-learn and torch 2.13.0+cpu all declare no
#     numpy upper bound and run fine on 2.4.6 (torch<->numpy interop verified).
#   * The codebase uses none of numpy 2.0's removed aliases (np.float_, np.NaN,
#     np.in1d, ...), no `copy=False`, and no removed methods (.ptp/.itemset).
#   * The guard's hash path is byte-identical under 1.26.4 and 2.4.6 — verified
#     by running its exact tobytes()/memoryview cast on fixed float32 patterns
#     under both. accurate_fingerprint.py is therefore NOT numpy-version-bound
#     and does not need re-pinning.
#
# CAVEAT worth carrying: Fast mode's diarization was only ever validated on
# numpy 1.x (the shipped v3.1.0 CI build used the old pin). Nothing in its numpy
# usage is 2.x-sensitive — it is float(np.mean(...))/np.std/np.mean(axis=1) — but
# "no breaking pattern found" is not the same as "smoke-tested". Do that before
# release (6.1).
numpy==2.4.6

# huggingface_hub is pinned to 1.24.0 ON PURPOSE — do not casually bump it.
#
# This is the version every Accurate-mode behaviour in this repo was built,
# debugged and verified against (135/135 tests, plus real end-to-end network
# runs of the Xet fallback and the kill-and-resume path). A throwaway size
# investigation happened to install 1.25.1 and pinned that incidentally; the
# 1.24.0 -> 1.25.1 range was reviewed commit by commit before choosing:
#
#   * HF_HUB_DISABLE_XET is STILL snapshotted into a module constant at import
#     time. accurate_model_download._xet_disabled() sets the module attribute
#     rather than just the env var precisely because of that, and the workaround
#     stays necessary. Nothing in the range fixes or changes it.
#   * The `<etag>.<uuid>.incomplete` file is still unlinked in a `finally`, so
#     resume is still per-file and never per-byte — the measurement the whole
#     chunked layout (2.1a.3) is built on still holds.
#   * xet_get() and the Xet progress reporting are untouched in the range.
#   * 1.25.0 swaps thread_map -> hf_thread_map in snapshot_download and
#     preupload_lfs_files, which changes how our custom tqdm_class is
#     instantiated. Verified our hook works under both shapes, so this is not a
#     blocker for a future bump — but it is a real change at a seam we depend on,
#     and it fixes a progress-ordering problem we do not have.
#   * 1.25.1 over 1.25.0 is a Jobs/Sandbox token change only. Not a path we use.
#
# Nothing in the range fixes a problem this app has, so the tested version wins.
# When bumping: re-run test_accurate_model_download.py in full (it exercises the
# Xet fallback and resume against the real Hub, not mocks).
huggingface_hub==1.24.0
